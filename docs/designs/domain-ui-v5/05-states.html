05 · Every state

Each window and section owns its states, in version 5's forms: the shared skeleton shaped like what is coming (review row 32); EmptyState, with a 14 px title and 12.5 px text, centred; WindowPlaceholder with Retry or Remove tab; PageWindow's "This window's file could not be loaded"; the struck-through tab of a window that is gone; UpdateBand for a notice in the shell; ServerCover while the server restarts. A window's state never touches its neighbours, because each window's prop carries its own result (design.md section 2, Data). A refresh in progress changes nothing on screen: the rows stay until the new ones arrive, as in version 5.

Window states side by side

1 First load: the prop is out, so the window draws its declared skeleton. 2 Empty. 3 Live update: the visible window's prop reloaded and the new row is tinted for 2 s; scroll, selection and drafts stay. 4 First load failed. 5 A refresh failed: the rows already shown stay, marked with when they were read (new). 6 Access lost: the reader's check now refuses, so the rows are removed, not kept as stale. 7 The window's component file failed to load. On a new build the tab reloads once; otherwise it says so (PageWindow). 8 The module was removed in a deploy: the tab is struck through and offers Remove tab.

Sections and counts: a section loading, a section failed, sidebar counts still out

A section in a slot keeps the host's frame while it loads (skeleton rows) and when it fails (one line, Retry). When it has nothing to show, or the person may not see it, the frame is absent, and so is the host's space for it. A dock card and a bar part follow the same rule: they show when they have something to show and are absent otherwise. A failed one is absent and logged. Sidebar counts arrive as a deferred prop. Until then, and for a count whose reader failed, the row shows no number.

Shell states: connection lost and a refused action

The live connection dropped: a strip in UpdateBand's form says so in words. Everything shown stays readable, and every window keeps working through plain requests. When the connection returns, every visible window reloads once and the strip goes. The chat refused a message: the draft stays in the composer and the reason sits under it. Nothing is sent again by itself.

Deploy: the server restarts, and Reload shows after a while

Installing or removing a module is a line in bootstrap/domains.php and a deploy. While the live connection is down and the health check fails, version 5's ServerCover blurs the shell. When the new build answers, the next Inertia request carries a different asset version, and the tab makes one full reload. Composer drafts survive it, because they live in session storage. If the server takes long, the cover offers Reload.
